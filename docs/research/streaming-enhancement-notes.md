# 边看边增强：可行范围与实时门槛

调研日期：2026-09-27。公开一手资料调研；未安装依赖、下载模型或影片、处理帧。本机能力查询来自主代理的只读核验，未在此重复执行。

## 结论

可以设计逐帧增强播放管线，但尚无证据承诺 M4 / 16GB 上所有片源稳态实时增强至 4K。V1 应包含普通播放、可立即切换的增强、过载回退；增强支持的输入尺寸、倍率、帧率由短片及持续播放原型决定。AI 输出 3840×2160 不等于恢复原生 4K 信息。

## Apple 原生低延迟路径已存在，但本机能力有明确限制

- 官方 `VTLowLatencySuperResolutionScalerConfiguration` 自 macOS 26 起提供，配置 `VTFrameProcessor` 做低延迟逐帧超分。它可查询系统支持、输入尺寸、倍率及像素格式。SDK提醒启动 session 的模型加载可能超过一帧时间，应避开 UI 及渲染阻塞：[配置文档](https://developer.apple.com/documentation/videotoolbox/vtlowlatencysuperresolutionscalerconfiguration)。主代理直接读取本机SDK头文件并查询运行时能力，路径、命令和输出见[能力记录](streaming-capability-probe.json)。
- [WWDC25 官方讲解](https://developer.apple.com/videos/play/wwdc2025/300/)把此类低延迟效果定位于实时接收端；需调用方管理像素缓冲池并提交帧。这是适用场景说明，未提供此 M4 的 fps 保证。
- 主代理在本机 M4 / 16GB / macOS 27 只查询能力：`isSupported=true`；`minimumDimensions=96×96`；`maximumDimensions=1280×1280`；1920×1080 与 1916×1080 的支持倍率均为空；1280×720 仅 `[1.5]`。未创建 session、下载模型或处理帧。
- 因此本机已发现的候选是 **720p → 1080p（1.5 倍）**，仍待运行测试；不能把 `isSupported=true` 宣称为 1080p → 4K。先缩小再增强至 1080p、最后普通放大到 4K 也不等同直接 AI 超分 4K，可能损失原有信息，不应默认采用。

## Real-ESRGAN / ncnn / Video2X

- [Real-ESRGAN](https://github.com/xinntao/Real-ESRGAN)是单帧图像修复。可常驻模型后逐帧送入，不要求未来帧，但跨帧稳定性不能由单张好看推导；细纹、脸和颗粒可能闪烁。每帧新建进程、加载模型或写 PNG 应避免。此为管线建议，不是已实现或已测的性能。
- [ncnn 实现](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan) CLI 接收图片/目录，支持分块和加载/处理/保存线程。将其嵌入播放器需要帧级接口与调度；官方说明未给本机 M4 稳态实时 4K 证据。其 [macOS 发布工作流](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan/blob/master/.github/workflows/release.yml)经 MoltenVK 走 Vulkan → Metal，存在 macOS 发布不等于已验证现代 M4 播放链。
- [Video2X](https://github.com/k4yt3x/video2x)当前主线支持 Windows/Linux，预编译包要求 AVX2，README 虽提 macOS 容器，其 [容器文档](https://docs.video2x.org/running/container.html)未建立 Apple GPU 可用链。不能承诺 M4 开箱即用。
- Video2X 的 [处理源码](https://github.com/k4yt3x/video2x/blob/master/src/libvideo2x.cpp)边解码、处理、编码并写输出，免整集帧文件，但这只证明可增量转码。它不是现成低延迟播放器；转码后再解码播放增加开销。其 benchmark 分支跳过写编码帧，单看该 fps 不能证明完整播放链实时。
- [BasicVSR++ 论文](https://arxiv.org/abs/2104.13371)利用时空传播；标准双向序列处理需要未来帧。分块能限制等待和内存，但前瞻增加启动/seek 延迟及块边界成本；改成因果模型需要重新验证质量。多帧修复不应成为 V1 默认实时路径。

## 缓冲的边界（管线推导）

设播放消耗 F 帧/秒、增强持续产出 R 帧/秒、初始缓存 B 帧。若 R < F，则缓存约 B/(F−R) 秒后耗尽。例如 24fps 播放、12fps 增强、缓存120帧（5秒视频），只能再支撑约10秒。有限 buffer 能吸收短时抖动，不能补偿持续算力不足。

24/30/60fps 的播放间隔分别约41.7/33.3/16.7ms。这不是单次模型推理预算：应测解码、颜色转换/拷贝、推理、排队、呈现的整条链吞吐与尾部延迟。慢于实时必须降低增强成本、回退普通帧或暂停等待；不能同时保证最高增强、无等待、无丢帧。

## 建议的 V1 与验证

1. 硬件解码 → 常驻增强器 → 呈现；验证上述 Apple 原生 720p/1.5 倍能力，ncnn等作为实验后端。普通 GPU 缩放/适度锐化作为低开销候选，其真实播放性能也需测；对真人剧不默认套动漫效果。1080p→4K仍需独立验证可用方案，720p→1080p不能替代这一目标。
2. 小而有界的帧队列、原始 PTS/音频主时钟；建议排队过载时降低增强成本并明确显示模式，保持音画同步。用户对流畅优先/画质优先的偏好尚待答复；画质优先可能需要暂停缓冲。字幕在增强后独立绘制，避免把可切换字幕烘入 AI 帧。
3. seek 时取消旧帧/旧请求并清空队列；带时间状态的算法需重置。切镜不能沿用无关历史帧；缓冲与前瞻越大，跳转代价越明显。首次显示普通画面，后台准备增强 session。
4. 先限定 SDR；查询实际像素格式与颜色属性，再验证 HDR。模型 RGB 路径不能直接假定保留 HDR 亮度、色域与元数据。受保护播放器不保证向自定义增强器提供可处理帧，应与已验证片源播放链一起验收。
5. 先用可用于测试的10秒片段筛选：480p/720p/1080p、24/30fps、运动/切镜/暗部/人脸/字幕；分别记录输出尺寸、端到端 fps、p95/p99 延迟、首帧/seek 等待、丢帧、队列峰值、内存和视觉闪烁。5–10分钟试跑后，对每个宣称支持的组合至少持续30分钟验证热稳定与队列不持续增长，另测倍速、开关增强、seek、切集和恢复；10秒测得快不代表整集稳态。若增强期间大量回退普通画面，不能将其记录为“持续AI超分通过”；必须单列各模式占比。
6. 可交付承诺应是“支持边播边增强及自动回退，列出通过验证的输入/倍率/帧率组合”。“任何低画质剧均实时达到真正4K”缺乏依据，不能写入已验收范围。

边界：这些建议尚未经过本机帧处理和播放原型验证。未联网传输用户视频，未使用另一台 GPU 或远程主机。
