# 个人影视播放器：需求与可行性评审 v0.2

日期：2026-09-27。本文保留需求确认阶段的调研结论。用户随后明确要求实现自制播放器，已据此完成首版架构、代码与应用构建；当前实现和验证结果分别见 `superpowers/specs/2026-09-27-cinema-design.md`、`开发进度.md`、`验收记录.md`。以下早期探测不是最终验收，尚未验证的原生4K、全集完整播放等目标仍不可视为完成。

## 1. 已确认的需求

| 项目 | 用户已确认的内容 |
| --- | --- |
| 用途 | 自己长期看电影、电视剧，首要代表作品为《怪奇物语》《绝命毒师》《火线》 |
| 设备 | Mac 桌面优先，后续扩展其他设备 |
| 资源 | 用户目前没有三剧可接入资源，必须由软件自动寻找网络片源；自己的链接和本地影片作为补充入口 |
| 播放 | 三部指定剧必须在软件内直接观看；跳转官方平台不算完成需求 |
| 画质 | 先找更高清的现有版本；需要增强时采用流式处理，边看边增强，争取4K观看效果，不等待整集处理完再播放 |
| 流程 | 先确认需求，查清三剧片源可行性，再进行架构设计，最后编码和验收 |
| 参考 | 借鉴Netflix、爱奇艺、B站的观影体验与GitHub开源项目 |

用户已进一步确认目前没有三剧可接入资源，需要软件自动寻找网络片源。因此首版不能依赖用户先准备本地文件、NAS、链接或平台会员；个人片库是补充能力，不能替代自动找源要求。

本次变更：用户明确要求“通过流式的方法进行画质增强，可以边看边进行处理”。这取代先前“可以等待本机离线处理完成”的主流程。流式增强已确认；处理赶不上播放时选择降低强度还是暂停缓冲，仍是待答偏好。下文的流畅优先仅为建议，未视为用户已经选择。

## 2. 调研结论

**已经发现三部剧的网络媒体候选，三个首集的小样本均通过本机解码；具备继续做播放验证的技术依据。尚不能承诺164集全部真实、完整、稳定地在本软件播放，也未验证来源许可和4K版本。**

官方平台路线与第三方聚合路线应分开判断：

- Netflix、HBO等官方页面可确认作品供应或发行信息，但本次没有取得面向本软件的通用正片播放接口。把官方网站放入WebView也需要验证服务兼容性，不能自动承诺4K。
- 《绝命毒师》有Stories by AMC等官方免费广告频道候选；Philo官方资料显示地区限制与线性排期，因此不能用它直接替代全剧任意选集。[官方频道入口](https://www.philo.com/player/show/U2hvdzo2MDg1NDg4OTk2NDg0NDk4OTY)、[地区说明](https://help.philo.com/using-philo/where/)
- LibreTV/MoonTV能参考多源搜索和集目处理，但视频来自独立来源。代码的开源许可证不能说明影片来源的授权情况。[LibreTV](https://github.com/LibreSpark/LibreTV)、[MoonTV旧仓库迁移入口](https://github.com/senshinya/MoonTV)
- Stremio官方帮助也区分内嵌可播内容与Netflix等需要跳转的内容；后者不满足本项目要求。[官方说明](https://stremio.zendesk.com/hc/en-us/articles/360000294431-What-can-I-watch-in-Stremio-with-the-official-add-ons)

### 2.1 实际网络探测

通过GitHub公开聚合项目的接口配置线索找到一个公开HTTPS目录，查询三剧的季集记录，读取每部S01E01的主/子HLS清单，再将首个媒体分片读入内存。使用本机ffprobe读取媒体参数，FFmpeg将其中2秒解码到空输出；没有保存影片文件或操作账户。每次媒体分片读取上限8MiB。

| 作品 | 目录声称的季/集覆盖 | 首集清单声明时长 | 首个分片实际探测 | 2秒解码 |
| --- | --- | --- | --- | --- |
| 怪奇物语 | 五季，8/9/8/9/8，共42集 | 48分05.81秒 | 1920×1080，H.264，约23.976fps，AAC双声道 | 退出码0，47帧，无错误输出 |
| 绝命毒师 | 五季，7/13/13/13/16，共62集 | 58分41.32秒 | 1916×1080，H.264，约23.976fps，AAC双声道 | 退出码0，47帧，无错误输出 |
| 火线 | 五季，13/12/12/13/10，共60集 | 63分00.84秒 | 1920×1080，H.264，约23.976fps，AAC双声道 | 退出码0，47帧，无错误输出 |

清单声称的宽高都是1080×608，实际分片却是上表尺寸。因此分辨率标签应采用实际媒体尺寸，并另外记录压缩质量与来源出处；尺寸不能证明原生制作分辨率或真实细节，1916×1080也不能写成1920×1080。三个主清单哈希相同，但子清单哈希、长度和分片不同；相同的相对路径模板本身不证明它们是同一个视频。

以上仅说明候选目录与三份短样本的传输/解码技术可行。**没有视觉确认整集身份，没有遍历164集媒体，没有全片播放、随机拖动、中文字幕或跨日稳定性验收，也未证明资源站对作品具有供应许可。**不能把HTTP成功或目录写着“已完结”当作全剧验收。结构化证据见[网络探测记录](research/network-source-probe.json)。

### 2.2 画质增强

“达到4K像素尺寸”和“恢复原生4K真实细节”是不同目标。建议产品明确区分：4K来源（制作/发行出处另记）、AI超分至4K、普通缩放至4K。损失严重的细节不能保证被真实恢复，模型可能产生闪烁、蜡感或错误纹理。

新的目标流程是网络数据按需读取 → 解码 → 对即将显示的帧增强 → 按原时间轴播放。无需等到下载或增强完整一集。增强器应常驻，以有界队列处理帧；同机直接观看优先直接呈现处理结果，不默认额外编码成分段文件再解码。具体播放内核与帧接口仍需架构比较。

| 候选方式 | 用途及当前证据 | 尚未证明的条件 |
| --- | --- | --- |
| GPU缩放、温和去噪/锐化 | 作为低开销候选，播放时可开关；须如实标记普通增强 | 当前内嵌后端的实际速度与观感，不能当作AI恢复真实4K |
| Apple低延迟超分 | 官方提供实时处理API；本机查询支持720p输入、1.5倍输出 | 当前1080p输入的支持倍率为空；没有帧处理或性能实测，不能直接承担1080p→4K |
| 常驻轻量模型或ncnn逐帧超分 | 不必等整集处理，可纳入原型比较；Real-ESRGAN是候选之一 | M4上的持续吞吐、模型兼容、跨帧闪烁、拷贝和内存成本；开源存在不等于实时可用 |
| 短段预处理后播放 | 可在允许等待时比较更强模型 | 有限缓存不能解决长期低于播放速度的问题；双向多帧模型有前瞻延迟，不默认作为首版实时路径 |

Apple官方区分高质量超分和面向实时处理的低延迟超分，见[WWDC25说明](https://developer.apple.com/videos/play/wwdc2025/300/)。本机只读查询结果为：`isSupported=true`、输入尺寸范围96×96至1280×1280；1920×1080和1916×1080支持倍率均为`[]`，1280×720为`[1.5]`。这只证明当前可查询的配置能力，未创建处理会话、下载模型或处理帧。查询证据与SDK位置见[能力记录](research/streaming-capability-probe.json)。先缩小1080p再增强并放大到4K会损失原有信息，不作为默认方案。

“流式”不自动等于“实时”：24fps视频在1倍速需持续产出约24帧/秒，2倍速需约48帧/秒。若增强只能产出12帧/秒，即使预存5秒视频（120帧），也会约10秒后耗尽缓存。因此建议正常观影采用流畅优先，算力不足时降低增强强度并明确显示模式；画质优先则允许暂停等待。此项偏好尚待用户答复，不能同时承诺最高增强、零等待和零丢帧。

先用10秒片段比较画质和排除不可行路线，再以至少30分钟持续播放验证通过的输入尺寸、输出尺寸、帧率与倍速组合。需记录全链吞吐、尾部延迟、丢帧、同步误差、队列峰值和热稳定；单次推理快或短片通过都不构成整集实时证明。详细依据见[流式增强研究](research/streaming-enhancement-notes.md)；[原算法与离线研究](research/enhancement-research.md)保留为背景，不再代表首版主流程。

### 2.3 本机条件

已只读核验：Apple M4、16GB统一内存、macOS27.0；内置屏幕3024×1964；Swift工具链与FFmpeg/ffprobe存在，当前PATH未发现mpv；目标磁盘可用空间约15GiB（动态快照）。这些信息不是4K播放或模型性能实测。

因此压缩网络缓存与解码帧队列必须分开，后者严格限量。仅一帧3840×2160 RGBA8画面约31.6MiB，5秒24fps原始帧已约3.7GiB，尚不含模型、解码器和系统占用。不能把几十秒缓存全部实现为4K原始帧常驻内存，也不能默认展开整集帧到系统盘。可取消增强、清理临时缓存并保留原片；整集增强导出不是观看的前置步骤。

内置屏分辨率不足以逐像素展示完整3840×2160画面；4K来源解码与缩放显示仍待验证，原生4K显示体验需在相应显示设备单独验证。

## 3. 首版需求提案：待确认

以下是建议范围，不把未确认的功能当成用户已经要求。

| 编号 | 建议要求 | 验收定义 |
| --- | --- | --- |
| F01 | 中文Mac桌面应用、统一内嵌播放器 | 在同一软件里完成搜索、选集、播放；启动另一个播放器窗口或浏览器不算通过 |
| F02 | 网络来源检索及来源管理 | 按真实提供者搜索并显示状态；作品资料、候选源、已实际播放分开；失效有明确原因，不能假造片库 |
| F03 | 三剧作为内容验收基线 | 三剧全部季集须具备匹配正确的可用正片来源，能由本软件内嵌播放；未解决的缺集、错集或不可播均不满足硬要求。逐集做基础探测，至少每季首/中/末集做代表播放与拖动测试，并报告未完整观看的范围。抽样是验证方法，不能替代全集可用条件；164个目录条目不自动算164集可用 |
| F04 | 本地与链接导入 | 文件/文件夹、MP4/MKV及已支持的HTTP(S)媒体；重复导入不制造重复条目；保留原文件。普通网页需具体适配，不能声称任意网页可播 |
| F05 | 电影/剧集库和追剧 | 季集排序、继续观看、待看、下一集；缺集时说明，不能跳过缺集；变更资源要核对同集及剪辑版本 |
| F06 | 必要播放控制 | 暂停、音量、拖动、全屏、倍速、键盘控制、音轨选择；持续播放和错误恢复有真实测试记录 |
| F07 | 中文字幕与英语音轨 | 内嵌轨道及外部SRT/ASS字幕作为候选范围，字体/时轴/换轨实际验证；没有字幕时明确显示，不伪造语言支持 |
| F08 | 高清版本优先 | 对比已匹配的同一集来源，综合清晰度、码率、语言和可用性；切源保留可恢复进度，原版本仍可选 |
| F09 | 边看边增强，争取4K效果 | 首版包含实际运行的SDR流式增强路径，不等待整集完成。播放中开关/A-B比较；显示源尺寸、增强后尺寸和真实模式。原型筛选后，每个宣称支持的组合至少持续播放30分钟，并测试拖动、倍速、切集和故障回退；逐项记录吞吐、丢帧、同步、内存与闪烁。只提供经过验证的档位；无可用AI路径不能以普通放大冒充AI超分，也不能用离线导出替代流式要求 |
| F10 | 数据与故障处理 | 历史/库默认本机保存，断网仍能看本地影片；不把访问令牌写入普通日志；来源失效、格式不支持和缺少访问条件分别提示 |

首页建议采用继续观看、我的剧集、最近添加、待看，详情页突出季集与真实资源；播放页突出字幕、版本和画质。借鉴成熟平台的操作习惯，不照搬品牌标志或把尚不可播的海报包装成已拥有的片库。

F09的交互与工程约束提案：

- 播放无需等整集下载或处理；模型初始化期间可先显示普通画面，准备好再启用增强。启动及拖动允许多长等待在技术验证后明确。
- 原始帧时间戳、音轨和字幕保持同步；软字幕在增强后绘制。开关增强不从头播放、不重置观影进度。
- 拖动或切集取消旧请求，清空过期帧，重置时域历史；源分辨率改变时重新检查增强配置。旧帧不得在新位置出现。
- 同时监测网络缓冲与增强排队，分别说明原因。队列有上限；处理不足时按所选策略降低成本或暂停等待，不能无限积压或静默标成“AI 4K”。测试单列实际增强与普通回退的占比，频繁回退不能算作持续AI超分通过。
- 温控、低电量模式和倍速改变均可能影响通过的档位，持续测试要覆盖；HDR增强另行验证，首版SDR能力不推及HDR。

后续再扩展Windows/手机、NAS同步、HDR端到端增强、远端GPU、弹幕和复杂推荐。当前不将这些扩展加进首版关键路径。

## 4. 软件工程阶段与通过条件

| 阶段 | 产物 | 通过条件 |
| --- | --- | --- |
| 需求与片源可行性（当前） | 本评审、来源探测记录、专题研究 | 用户确认首版功能与三剧验收口径；说明采用来源路径和未解决条件 |
| 架构设计 | 界面流程、播放内核/来源适配/媒体库/增强任务的职责与数据流、选型理由及失败处理 | 对网络源播放、原生内嵌和Mac增强等高风险点给出可验证方案，再审阅书面设计 |
| 实施计划 | 按依赖拆分的步骤、技术验证清单、测试与交付安排 | 审阅计划后再进入代码实现，先验证影响选型的能力 |
| 技术验证 | 小型内嵌播放验证、三剧样本运行记录、10秒画质比较及至少30分钟流式增强报告 | 验证播放内核能承载实际增强器，并明确输入/输出/帧率的可用组合；仍不能据此宣称完整软件完成 |
| 编码 | 可构建源码与运行说明 | 顺序完成查找/导入→播放→季集/续播→字幕/换源→增强，按实际进展测试 |
| 验收与交付 | Mac应用、测试报告、依赖/来源说明 | 用户真实观影流程可用且F03硬要求成立；报告通过/失败/未测组合。存在未解决的缺集、错集或不可播时只能交付未完成版本，不能把列出限制当作通过 |

已有初步技术比较：Mac优先时SwiftUI/AppKit+内嵌libmpv值得评估；跨平台桌面和Web路线分别有收益与额外成本。**该候选没有被锁定成最终架构**。新增流式要求后，必须比较libmpv内置渲染/shader路线与可直接访问像素缓冲的原生处理路线；不能假定libmpv可直接接入VideoToolbox/Metal超分而没有格式转换和拷贝成本。播放兼容性、帧级接口、字幕及同步管理共同决定选型。详见[播放内核研究](research/playback-research.md)。

## 5. 决策建议

建议以更新后的F01–F10推进需求评审，把三剧网络源作为必须验收的实际对象；架构阶段同时解决“真实正片身份、季集覆盖、软件内播放”和“持续流式增强”的验证方案，再安排影视库及其余实现。用户已明确流式方式，不需要再次确认该方向；处理过载偏好待答。当前研究支持继续设计和验证，不支持宣称全剧或全4K已经解决。

本轮不需要决定配色、软件名称或每个快捷键。关键是确认：上述首版范围与验收方式是否符合用户希望。全集可用是通过条件；“逐集基础探测＋每季代表集播放测试＋如实列出未测范围”是取得证据的方法，不允许以抽样通过掩盖已知缺集、错集或不可播。
