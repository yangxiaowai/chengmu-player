## 二、图像增强与广告识别共用解码

### 实现

- `CinemaVideoView` 在增强取样时刻把同一张已解码帧渲染为 960×540 静帧，交给 `AdSkipController.harvest(image:time:)`；转换在独立的 utility 队列完成，不阻塞增强 worker。
- `AdSkipController` 将当前几秒留给增强路径共用帧，独立解码器只预读更远的未播放画面；同一取样点互相避让。增强帧长期未到时，短暂等待后由独立路径补扫。
- 共享帧与独立帧共用同一套规则：同一 OCR、同一分类器、同一区间构建、同一 PTS 校验与去重。
- 原片模式、HDR 原生路由或增强不可用时使用原有独立解码路径。前方预读仍需额外解码与网络带宽；单靠当前播放帧无法提前跳过广告。

## 六、播放失败的错误码与并发连接修复

用户报告播放时出现“当前资源无法播放（错误 -1008）”与“（错误 -12889）”。核对后：

- `-1008` 是 `AVErrorContentIsUnavailable`：来源暂时不提供媒体数据（网络或来源侧限制）。
- `-12889` 是 `AVErrorMediaServicesWereReset`：系统媒体服务被重置，播放期间音频或显示设备发生变化时常见。
- 两者都不是“封装/编码不支持”。旧的统一个文案把它们错报成编码问题，现已改为按错误码给出原因，并区分网络错误与媒体错误。
- `docs/` 全量检索：本轮之前的所有验证产物中**从未出现过**这两个错误码，可复现的本地与合成素材上也未复现，因此不能归因为本轮代码回归。

不过本轮确实引入了一个真实风险并已修复：`MediaExperienceInspector` 会为同一个 item 再次发起 `loadTracks`/`loadMediaSelectionGroup`，与主播放、HLS 探测、广告扫描叠加后，同一 URL 上最多有 5 个并发消费者。对慢速 HLS 来源，这些并发连接可能让主播放的传输失败。

### 定位到的实际原因（非凡等网络来源无法起播）

用户随后报告：非凡目录此前可以播放，升级后固定报 -1008。逐项核验：

| 检查 | 结果 |
| --- | --- |
| 非凡目录接口 | 通过：搜索 7 条、详情 1 条线路 8 集 |
| 媒体清单 | 通过：主清单 200、子清单 200（491 分片、1964 秒、未加密） |
| 首分片 | 通过：HTTP 206 / 200，`Accept-Ranges: bytes`，实际取到 2.3MB |
| 应用自带来源探测 | `catalog=true playlist=true segment=true passed=true` |
| **真实网络 HLS 起播** | 通过：单消费者播放推进到 28.9 秒；再加一个并发消费者仍推进到 27.7 秒 |
| **10bit 转换输出是否阻断起播** | 不阻断：无输出 / 10bit / 32BGRA 三种情况都推进到约 6 秒且 12/12 次都取到帧 |

真正的原因在检查器里：`MediaExperienceInspector` 用了 `AVPlayerItem.asset.tracks`。这是 **已废弃的同步访问器**，对网络 asset 会触发阻塞式加载——它在描述播放的同时把播放本身拖住，网络来源因此报 -1008，而本地合成素材完全没有这个问题，所以本地验证一直是绿的。

修复（三条，全部已验证）：

1. 检查器改为**完全被动**：只读 `AVPlayerItem.tracks`（始终在内存中），彻底移除 `AVAsset.tracks`；轨道尚未暴露时报告为未知，交给逐帧色彩门禁，而不是再去加载。音频信息由 `PlaybackController` 在 `prepareReady` 中把已经异步加载好的音轨组交给检查器复用。
2. 广告扫描的独立解码器改为**等主播放就绪并已推进**（`status == .readyToPlay` 且 `position > 0.05`）后才启动，避免在首帧出现前就与主播放抢连接。
3. 新增 `scripts/validate-passive-media-inspection.sh`：静态检查应用代码中是否再次出现 `.asset.tracks`、`.asset.duration`、`.asset.isPlayable`、`.asset.preferredTransform`、`.asset.mediaSelectionGroup` 等废弃同步访问器，并确认仍在使用 `loadTracks(withMediaType:)` 与 `loadMediaSelectionGroup`。反向验证：人为把 `item.asset.tracks` 加回去，脚本以 1 处违规失败；移除后通过。

## 七、新增的两个画面开关

用户要求「添加一个杜比的开关和切回原片的开关」。杜比本身没有开关可言（不代表能凭空开启或升级），因此落地为两个**诚实**的控制：

| 开关 | 位置 | 实际行为 |
| --- | --- | --- |
| 实时画质增强（开 / 关） | 播放控制栏「画质增强」菜单 + 视听适配面板 | 关闭即**切回原片**：摘除转换输出、显示系统原生层、停用去噪/锐化/放大与广告柔化；不重建 item、不打断时钟 |
| 杜比视界与 HDR 原生直通 | 视听适配面板 | **始终开启且置灰不可关闭**，并写明原因：改写像素会让杜比视界的逐帧动态元数据失效 |

偏好持久化在 `PlaybackPreferences.pipeline`（`enhanced` / `original`），旧存档缺字段时默认 `enhanced`，非法值不会被当成关闭。切回原片不会改变片源、所选轨道、字幕时间轴或音频策略。

验收（`hdr-render-green.json`，共 18 项）：

- `enhancement_runs_before_the_switch`：切换前增强确实在跑（1 帧已处理、1 个转换输出）。
- `original_switch_detaches_the_conversion_output`：切换后转换输出为 0 且显示原生层。
- `enhancement_switch_restores_processing_without_rebuilding`：切回后同一个 item、重新挂上输出并再次产出增强帧。

同时修正了一个由此暴露的既有缺陷：`reset()` 先发布空指标、后计算路由原因，会把「为何不叠加柔化」的说明擦掉。现在先算原因再发布，PQ/HLG 两项检查因此恢复通过。

## 八、真实网络源起播验证与第二轮修复

用户第二次报告非凡报 -1008。这次不再依赖清单探测，而是**用生产代码路径直接播放真实非凡流**（`PlaybackController` + `CinemaVideoView` + 检查器 + HLS 探测 + 广告扫描全部在线）。

### 结论（混合预读调度修改之前的网络记录）

| 检查 | 结果 |
| --- | --- |
| 非凡各端点 | 主清单 200、子清单 200、分片 206/1MB；连续 8 次主清单请求全部 200，**无速率限制** |
| 生产路径完整播放 | **推进 37.0 秒、处理 809 帧 GPU 4K 增强、0 错误、0 回退** |
| 用户当时的构建 | 偏好文件里没有 0.2.9 才写入的 `pipeline` 字段 → **用户运行的是修复前的构建** |

### 这轮实际修掉的两个缺陷

1. **片源评估每个 tick 重跑一次**：`tick()` 里 `assessed !== player.currentItem` 的判断会在 item 就绪前后反复触发 `reset()`，把已经成功的路由重新改写成「正在评估片源色彩」并摘掉输出。现在评估**每个 item 只做一次**（`assessedFormatKnown`），item 变化时才重置。
2. **转换输出重复挂载**：`output == nil` 不足以判断，残留引用会让同一个 item 上叠第二份全分辨率帧拷贝。现在按自身引用判断，重复调用幂等。

### 另外新增的容错

`AVPlayerItemFailedToPlayToEndTime` 在链路抖动时也会触发，此前一律直接判失败。现在**同一集自动静默续播一次**（保持片源、线路与播放意图不变，回到中断位置前 0.5 秒），只有第二次中断才提示错误，避免把一次短暂丢包变成一次播放失败。

## 九、画面开关的后续修复（4K 无法开启）

用户报告「现在不能开启 4K 了」。存档显示 `pipeline: "original"`、`enhancement: "upscale4K"`：用户把「实时画质增强」关掉了，而模式菜单**照常显示所有档位、点了却毫无反应**，也没有任何说明——这是我的设计缺陷，不是 4K 本身坏了。

修复（`scripts/validate-picture-switch.sh` 固化）：

1. 关掉开关后，选择任一增强档位会**同时把开关打开**，模式立即生效，不再被静默吞掉。
2. 选择「原片」等价于切回原片（开关同步关闭）。
3. 菜单里当前档位带 ✓ 标记，底部状态行直接写出当前档位；关掉时提示「选择上面任一项即恢复增强」。

复现与验证（真实 `PlaybackController` 偏好处理，无窗口、无媒体）：

```
default:            pipeline=true  surfaceMode=upscale4K enhancement=upscale4K
after switch off:   pipeline=false surfaceMode=original
after choosing 4K:  pipeline=true  surfaceMode=upscale4K enhancement=upscale4K
PASS choosing 4K restores the pipeline
```

同时确认 4K 增强本身工作正常（Apple M4 合成帧基准）：`upscale4K -> GPU 增强至 4K, output [3840, 2160], 240 帧, 平均 14.7ms`。

## 十、画质档位的实测：4K 到底改了什么

用户反馈「选到 4K 但感觉画质没变化」。这可以量化，于是新增 `scripts/validate-picture-modes.sh`：把静态 1920×1080 素材真的送进 `EnhancementPipeline`，测量平均亮度、边缘细节（相邻像素平均差），以及**经过播放器显示缩放后还剩多少**（视频区约 1234pt 宽 × 2 倍 Retina ≈ 2468 像素）。

| 素材 | 档位 | 输出 | 平均亮度 | 细节（1:1） | 显示缩放后 |
| --- | --- | --- | --- | --- | --- |
| SMPTE 彩条 | 原片 | 1920×1080 | 92.61 | 0.147 | 0.122 |
| SMPTE 彩条 | GPU 清晰增强 | 1920×1080 | 92.64 | 0.194 | 0.154 |
| SMPTE 彩条 | GPU 增强至 4K | **3840×2160** | 92.69 | 0.193 | **0.176** |
| 平滑渐变 | 原片 | 1920×1080 | 44.58 | 0.020 | 0.018 |
| 平滑渐变 | GPU 清晰增强 | 1920×1080 | 44.58 | 0.020 | 0.018 |
| 平滑渐变 | GPU 增强至 4K | 3840×2160 | 44.58 | 0.023 | 0.021 |

结论：

1. **4K 确实生效**：输出尺寸真的变成 3840×2160，边缘细节从 0.147 提升到 0.193，经过显示缩放后仍从 0.122 提升到 **0.176**，是三个档位里显示后最清晰的。
2. **颜色没有偏差**：平均亮度 92.61 → 92.69（0.09%），渐变素材完全相同；脚本把「增强档位导致平均亮度偏移超过 1%」设为失败条件，防止再次出现色彩损伤。
3. **为什么"感觉不明显"**：只改约 1–2% 的像素（平坦区域的去噪与缩放几乎不动像素），细节提升约 27%。对已经干净的 1080p 片源，这个幅度偏细腻而非肉眼可辨的跳变；在平滑渐变素材上清晰增强几乎是 0 差异，属正常。
4. 早期用 `testsrc2` 动态测试卡测出"亮度掉 18%"是测试卡自身高频图案在缩放下产生的混叠，不是管线问题；换成静态素材后差异消失，这也是本脚本改用 `smptebars` 与 `gradients` 的原因。

## 十一、"杜比/HDR 原生直通"不再做成开关

用户反馈这个开关一直选中、希望取消。它本来就不该以开关形式出现——杜比视界改写像素会让动态元数据失效，这不是偏好而是约束。现在改为**带锁图标的说明行**：

> 🔒 杜比视界 / HDR：固定原生直通
> 这不是可切换的选项。改写像素会让杜比视界的逐帧动态元数据失效，所以杜比与 HDR 片源一律交给系统原生呈现；上面的增强开关只作用于 SDR 片源。

## 十二、关闭 HDR 增强

用户明确要求「把 HDR 增强关闭」，并选择彻底移除。因此：

- 删除 `picturePriority` 与 `PlaybackPreferences.pipelinePreferSDR`：画面策略回到两态——「实时画质增强」开（SDR 增强 + 杜比/HDR 原生直通）/ 关（原片直通）。
- 视听适配面板不再提供任何 HDR 处理档位，改为一条固定说明：**杜比视界 / HDR：不做增强，固定原生直通**，并写明原因是改写像素会让逐帧动态元数据失效。
- 检查器里用于探测「是否有可选 SDR 画面版本」的代码一并移除，不再提示一个本应用无法执行的选项。
- 旧存档里若残留 `pipeline: "preferSDR"`，回退为 `enhanced`，不会把已删除的模式带进新版本。

验证（真实 `PlaybackController` 偏好处理）：

```
default:            pipeline=true  surfaceMode=upscale4K
原片直通:            pipeline=false surfaceMode=original
选择 4K:            pipeline=true  surfaceMode=upscale4K
legacy preferSDR -> enhanced processes=true
PASS two states, HDR enhancement removed
```

第 1 节与第 10 节的 HDR 路由验收（18 项）保持通过：杜比视界与 HDR 依旧只走系统原生层，逐帧色彩门禁仍然拦截未经确认的 HDR 帧。

## 十三、本轮明确未做的事

- 没有把硬件能力、清单声明或双声道空间化写成“正在输出杜比”。
- 没有下载整片、保存视频帧或上传任何画面。
- 没有修改系统音量、亮度、显示或音频设置。
- 没有新增第三方依赖或播放器内核。

## 十四、共享帧与前视预读补验

最初的共享帧实现会在收到当前帧时取消独立扫描，并持续延后它的恢复。合成片在 16–28 秒插播时，这会导致扫描器无法在观众看到广告前确认区间。新增回归先复现了这一点：共享帧已接受，但 9 秒内只有 1 帧被分析、前方区间不存在。修复后，同一测试在播放位置保持 0.2 秒时识别出 16–26 秒；完整 `PlaybackController + CinemaVideoView + Vision` 路径中，增强处理 336 帧、交出 9 帧、扫描器接收 4 帧，主播放器从约 16 秒跳到 26 秒。

当前帧与前方帧承担不同任务：共用当前帧避免同一取样点二次解码；要提前跳过内容内嵌广告，仍须独立预读未来。增强画面按 2 秒媒体时间栅格交帧，扫描器把近处 8 秒留给共用帧，预读更远处；共用帧若没有持续到达，短暂等待后恢复独立扫描。停止、换片和手动跳转会取消旧任务，过期结果不会污染新片。HLS 的前视预读可能额外占用带宽，真实网络来源的稳定性仍需逐源验证。

传输回归还暴露出自动续播的两处问题：一次自动重试被错误地计入之后新打开的影片；媒体尚未准备好时，重试从显示位置 0 秒恢复，丢失了预设的 52 秒定位。现在自动重试额度只沿同一媒体的内部替换继承；新打开的影片获得自己的额度，准备期优先保留待定位位置。`playback-stability.json` 的 15 项真实 AVPlayer/本地与本机 HTTP 测试均通过。

本轮复验：152 项 CinemaCore 测试、18 项 SDR/PQ/HLG/未知色彩路由、14 项广告 OCR/区间、9 项共用帧与完整播放链路、10 项自动跳过与字幕时间轴、15 项播放稳定性，以及音频策略与画质开关检查通过。上述插播样片是本地合成画面，不是网络来源准确率或真实杜比呈现证明；官方杜比样本仍未推进播放。

隔离原生窗口额外复现了暂停首帧的色彩标记竞态：同一 BT.709 合成片的暂停帧可能短暂报告 `ColorPrimaries#2`（未指定），旧逻辑误判为 HDR 并永久锁定原片。现在该帧只暂时使用原生层，等后续帧色彩标记确定后恢复增强。原生窗口已见到 `960×540 → 3840×2160 · GPU 增强至 4K`；播放位置 10.5 秒时菜单报告“已识别 1 段 · 已分析 20 帧”，帧来源为“复用播放帧 + 前方预读”；继续播放出现“已跳过插播主段 00:16–00:26”，点击“撤销并暂停”回到 16 秒且显示原时间轴字幕。使用的是独立 `AdSkipUINativeQA.app` 与隔离资料目录，未启动正式应用或修改个人片库。该检查记录在 `native-ui-green.json`，只覆盖本地合成片和列出的交互。

一次并行构建/回归运行中，2× 播放的合成片未在进入广告前完成扫描；随后三次单独运行同一组合验收均通过，隔离原生窗口也通过。故不把高负载下的提前跳过视为已保证。上文非凡 37 秒网络播放记录发生于混合预读调度修改之前，本次最终包没有再次在该远程流上实测；实际来源稳定性仍须逐源验证。发布包的签名、ZIP CRC、UTF-8 文件名及应用/压缩包二进制一致性见 `release-manifest.json`。
