# 映川 v0.3.3：实时 4K 输出与计算瓶颈实测

日期：2026-09-29；本机 Apple M4 / 16 GB / macOS 27.0。发行 build 15，入口 `dist/映川.app`，安装包 `dist/映川-v0.3.3.zip`。本机 ad-hoc 签名，非公证或商店发行。

## 这次改变

“流式修复”保留当前帧＋过去一帧的时域降噪，按设备实际支持使用 Apple 低延迟 AI。随后将低于 4K 边界的画面按原比例放大：720p 在本机先 AI ×1.5，再插值至 4K；1080p 没有系统低延迟 AI 倍率，走时域降噪＋细节保护插值至 4K。播放状态明确标记“细节缩放（非 AI）”，不把插值声称为原生 4K 细节恢复。

新增 Metal 内核使用经典 Catmull–Rom 插值，与双线性插值按局部对比度及梯度方向一致性混合；用最近 2×2 像素范围限制负瓣过冲，不额外锐化。平坦或梯度混乱区域减少细节权重，以降低残余噪点和压缩边缘的放大。插值、限幅及最终 sRGB 编码合并为一遍 GPU 计算，省去额外的 4K 中间纹理回写。源纹理仅在串行 worker 中复用，显示结果每帧独立持有，等待 GPU 完成后交付。

这是经典方法的工程组合与实现优化，不是已证明的新学术算法。原片、自然降噪、平滑 4K、Apple AI 单独模式均保留。最终 SDR 输出仍为 BGRA8；HDR/杜比片源继续原生呈现。单帧在途、迟帧丢弃、持续超预算退回原片、外置字幕和既有广告检测流程保留。

## 为什么“全部交给 GPU”仍不够

[EfRLFN 优化研究](research/efrlfn-optimization-2026-09-29.md)记录同一官方 x2 模型的真实完成时间、逐算子计划及等价变换验证。720p 默认配置约 122.55 ms，CPU＋ANE 120.12 ms，CPU＋GPU 442.60 ms；1080p CPU＋ANE 320.95 ms。仅模型推理已经超过 24 fps 的 41.67 ms 帧预算。

默认 Core ML 计算计划将约 99.547% 的**预测计算成本**安排给 ANE；这不是实测设备利用率。两种 ECA 等价图改写仍约 120–123 ms，52→64 通道补零反而约 141–143 ms。数值等价和实际输出已验证，不能把计时抖动写成加速成果。瓶颈主要在卷积计算量，因此没有将这个模型强行放进播放链路，也未将 Python 或模型权重打进发行应用。

局部包络限幅参考了 [AMD FSR1 EASU 的抗振铃原则](https://github.com/GPUOpen-Effects/FidelityFX-FSR/blob/master/ffx-fsr/ffx_fsr1.h)，本次内核为自行编写的经典插值实现，未移植 AMD 源码。原生高质量 VT 与其他空间缩放方案的试验另见研究记录。

## 验证

- `bash scripts/swift.sh test`：156 项、19 suites 通过。
- `bash scripts/validate-streaming-restoration.sh docs/validation/v0.3.3/streaming-restoration.json`：35/35；720p/1080p 实际 3840×2160、真实模式标签、seek/streamID/切镜参考边界、旋转、HDR 拒绝和局部柔化。柔化选框之外与字幕保护区的改变像素均为 0。
- 目标尺寸与标签断言先对旧实现运行，明确得到 4 项失败，见 `streaming-target-red.json`；生产实现通过后再归档绿色报告。
- 独立源码审阅见 [review.md](validation/v0.3.3/review.md)，覆盖颜色编码、纹理生命周期、HDR 门禁与字幕/柔化接入。

- [独立缩放验证](validation/v0.3.3/detail-scaling.json)：19/19。64→192阶跃无过冲，10–90%过渡2px，B-spline为3px；同一时域降噪结果的平坦区噪声MSE相对双线性最大约1.044倍。1080p→4K缩放单段60个热帧完成均值3.58ms、p95 4.63ms；不包含解码、降噪或屏幕显示。
- [1080p实际播放](validation/v0.3.3/restoration-playback-1920x1080.json)及[720p实际播放](validation/v0.3.3/restoration-playback-1280x720.json)：分别14/14。真实AVPlayer＋CinemaVideoView，合成SDR24fps片，起播/暂停seek/原片对照/恢复/实际4K尺寸均通过；稳态约3.1秒采样窗口内，1080p为75个完成帧、处理采样均值25.10ms；720p为76个完成帧、均值26.20ms，均未回退。计数分别约23.94及24.23帧/媒体秒，不是屏幕显示FPS、音画同步或长片温控证明。
- 播放测试首次使用每0.5秒节流的UI回调计数，窗口端点存在滞后；旧JSON/log保留为`*-published-counter.*`。最终新增只读诊断快照，按主线程当前计数取窗口两端，不改变生产调度或放宽阈值。`droppedTicks`是忙碌时timer tick累计，不能当作丢失视频帧数。
- [显示及HDR验证](validation/v0.3.3/hdr-render-color-fixed.json)：25/25，包括输出色彩标签与实际写入sRGB一致、PQ/HLG原生、HLS、原片切换与失败恢复。处理耗时表是在最后显示层色彩标签修正前采样；离屏处理算法与调度未因此变化，最终可见播放另有手工验收。
- [可见界面验收](validation/v0.3.3/visible-ui.md)：隔离QA实际选择流式修复、观看上下文字及外置字幕、原片对照和恢复播放。发现并修复已有增强显示层未标记sRGB导致的明显提亮；同帧对照确认该可见差异消失。这不是逐像素屏幕色准认证。
- Release编译、严格签名、ZIP CRC/字节匹配、UTF-8文件名、ditto解包及可执行权限验证通过。[发布清单](validation/v0.3.3/release-manifest.json)保存各文件SHA256；归档v0.3.2所有应用文件与上版发布清单一致。没有宣称片库文件逐字节未变，因为本轮未预先取得完整片库哈希快照。

### 小样本质量比较

《Tears of Steel》同一帧的两种退化，输入480×200→960×400。**(CC) Blender Foundation | mango.blender.org**，CC BY3.0；片段、许可、生成方法见[上一轮真实影片协议](research/film-restoration-validation-2026-09-28.md)。本项只比较空间缩放，不混入时域历史。

| RGB PSNR / dB | 新细节缩放 | B-spline | 双线性 |
|---|---:|---:|---:|
| 加噪样本 |32.346|31.692|32.303|
| 压缩样本 |30.871|30.418|30.892|

两例都高于旧平滑核，压缩例略低于双线性0.021dB；不能称为所有指标全面提升。初版独立harness误把柔化坐标检查的`downMirrored`读回用于影片，出现约7.3dB的错误评分；最终先验证旧CI纹理与直接CI完全一致、新缩放纹理与旧纹理方向一致，再按真实VideoSurface相同约定读取。生产shader未因这项测试错误改变。

未做广泛真实电影动态盲看、长片温控、4K60或所有屏幕/帧率验收。新路径仍是降噪、有限系统AI倍率与插值的组合，不保证补回被压缩删除的真实细节。
